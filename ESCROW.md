# Безопасная сделка: холдирование + сплитование

Деньги покупателя не попадают продавцу сразу. Они замораживаются на карте,
товар передаётся, и только после подтверждения приёма платёж списывается и
делится: выручка — продавцу, комиссия — площадке.

Схема одна, а провайдеров два — **ЮKassa** и **CloudPayments**. Различия
спрятаны за интерфейсом [`PaymentGateway`](src/lib/payments/types.ts):
логика сделки ([`purchase-fulfillment.ts`](src/lib/purchase-fulfillment.ts))
о конкретном сервисе не знает.

| | ЮKassa | CloudPayments |
| --- | --- | --- |
| Холд | `capture: false` при создании платежа | двухстадийная схема (`paymentSchema: "Dual"`) |
| Оплата | редирект на страницу ЮKassa | виджет на странице площадки |
| Списание | `POST /payments/{id}/capture` | `POST /payments/confirm` |
| Сплит | `transfers` внутри `capture` | выплата из накопления «Безопасной сделки» (`payments/token/topup`) |
| Реквизиты продавца | `account_id` магазина в «ЮKassa для платформ» | токен карты для выплат |
| Снятие холда | `POST /payments/{id}/cancel` | `POST /payments/void` |
| Возврат | `POST /refunds` с `sources` | `POST /payments/refund` |

Провайдер выбирается покупателем на странице товара (если настроены оба)
и фиксируется в `Purchase.paymentProvider`: подтверждать и возвращать
платёж нужно там же, где он был создан.

## Сценарий сделки

| Шаг | Что происходит | Код |
| --- | --- | --- |
| 1 | Покупатель оформляет заказ. Создаётся платёж с холдом — средства авторизуются и замораживаются на карте | [`/api/payments/create`](src/app/api/payments/create/route.ts) |
| 2 | Провайдер сообщает о заморозке. Покупка переходит в `HELD`, покупатель получает файл и лицензионный ключ | [`holdPurchase`](src/lib/purchase-fulfillment.ts) |
| 3 | Покупатель нажимает «Подтвердить получение». Деньги списываются и делятся: выручка — продавцу, комиссия — площадке | [`/api/purchases/[id]/confirm`](src/app/api/purchases/[id]/confirm/route.ts) → [`settlePurchase`](src/lib/purchase-fulfillment.ts) |

Если покупатель молчит, сделку подтверждает фоновая задача — через
`ESCROW_AUTO_CONFIRM_DAYS` дней (по умолчанию 3), но всегда раньше, чем
провайдер снимет холд сам (обычно 7 дней с момента авторизации).

## Статусы покупки

```
PENDING ──(средства заморожены)──► HELD ──(списание)──► COMPLETED
   │                                │                       │
   │                                │                       └─(refund)─► REFUNDED
   │                                └─(отмена / истёк холд)───────────► REFUNDED
   └─(платёж отклонён)──────────────────────────────────────► FAILED
```

Товар доступен для скачивания уже в `HELD`: подтверждать покупателю нужно то,
что он реально получил.

## Куда уходят деньги

Сплитование включается, если продавец указал свои реквизиты **у того же
провайдера**, через которого платит покупатель (раздел «Доходы» кабинета
продавца):

- **ЮKassa** — `User.yookassaAccountId`. При `capture` передаётся
  `transfers: [{ account_id, amount: <вся сумма>, platform_fee_amount: <комиссия> }]`.
  Продавец получает `amount − platform_fee_amount` на свой счёт, внутренний
  баланс площадки не участвует. Сумма всех `transfers[].amount` должна
  совпадать с суммой платежа — комиссия удерживается внутри трансфера;
- **CloudPayments** — `User.cloudpaymentsPayoutToken`. Платёж открывает
  накопление «Безопасной сделки» (`escrow: { startAccumulation: true,
  escrowType: "OneToN" }`), а при подтверждении из него делается выплата
  на карту продавца (`payments/token/topup` с `FinalPayout: true`).
  Комиссия площадки — то, что осталось невыплаченным;
- **реквизиты не указаны** — платёж обычный, деньги приходят площадке,
  а продавцу начисляется внутренний баланс (`User.balance`) с выводом
  через заявку.

Если выплата продавцу по CloudPayments не прошла, деньги уже списаны с
покупателя и остались у площадки — выручка зачисляется на внутренний
баланс, а в лог пишется ошибка. Сделка при этом не срывается.

## Споры

Решение спора зависит от того, списаны деньги или ещё заморожены
([`/api/disputes/[id]/resolve`](src/app/api/disputes/[id]/resolve/route.ts)):

| Состояние | Отказ в споре | Полный возврат | Частичный возврат |
| --- | --- | --- | --- |
| `HELD` | списание всей суммы | снятие холда — деньги остаются у покупателя | списание части суммы, разницу провайдер возвращает сам |
| `COMPLETED` | ничего | возврат на всю сумму | возврат на часть суммы |

Пока спор открыт, подтвердить сделку нельзя, а автоподтверждение её не трогает.
Если спор не решён до конца срока холда, фоновая задача снимает холд —
списать деньги после истечения авторизации всё равно невозможно.

Возврат по ЮKassa забирает долю продавца с его счёта (`sources`).
CloudPayments так не умеет: возврат делает площадка со своего терминала,
а долг продавца уходит в минус на внутреннем балансе и гасится
следующими продажами.

## Что настроить в ЮKassa

1. Подключить «ЮKassa для платформ» и получить `account_id` для каждого продавца.
2. Включить двухэтапную оплату в настройках магазина.
3. В разделе HTTP-уведомлений указать `https://<домен>/api/payments/webhook`
   и включить события:
   - `payment.waiting_for_capture` — деньги заморожены, выдаём товар;
   - `payment.succeeded` — списание подтверждено;
   - `payment.canceled` — платёж отменён или холд истёк;
   - `refund.succeeded` — прошёл возврат.

Уведомления принимаются только с [официальных адресов ЮKassa](https://yookassa.ru/developers/using-api/webhooks),
а их содержимое перепроверяется запросом к API.

## Что настроить в CloudPayments

1. Подключить «Безопасную сделку» через персонального менеджера: для неё
   заводятся **два терминала** — оплат и выплат. Оплаты и выплаты по этой
   схеме идут только по картам.
2. Ключи обоих терминалов положить в окружение:
   `CLOUDPAYMENTS_PUBLIC_ID` / `CLOUDPAYMENTS_API_SECRET` и
   `CLOUDPAYMENTS_PAYOUT_PUBLIC_ID` / `CLOUDPAYMENTS_PAYOUT_API_SECRET`.
   Без терминала выплат сплитование выключено: платежи будут работать,
   а выручка пойдёт через внутренний баланс.
3. В настройках сайта включить уведомления и указать для каждого свой
   адрес — тип передаётся query-параметром, потому что в теле запроса
   его нет:

   ```
   https://<домен>/api/payments/cloudpayments/webhook?type=check
   https://<домен>/api/payments/cloudpayments/webhook?type=pay
   https://<домен>/api/payments/cloudpayments/webhook?type=fail
   https://<домен>/api/payments/cloudpayments/webhook?type=confirm
   https://<домен>/api/payments/cloudpayments/webhook?type=cancel
   https://<домен>/api/payments/cloudpayments/webhook?type=refund
   ```

   Формат уведомлений — любой из двух (form-urlencoded или JSON).

Уведомления принимаются только с адресов CloudPayments и с верной
HMAC-подписью (`Content-HMAC` / `X-Content-HMAC`), а состояние транзакции
перечитывается запросом к API.

`check`-уведомление — это ещё и защита суммы: виджет запускается на
стороне покупателя, поэтому перед списанием площадка сверяет `InvoiceId`
и сумму с покупкой и отклоняет платёж, если они не сходятся.

## Фоновая задача

```bash
curl -X POST https://<домен>/api/cron/settle-holds \
     -H "Authorization: Bearer $CRON_SECRET"
```

Запускать раз в 10–15 минут (cron, systemd timer, Kubernetes CronJob). Задача:

1. подтверждает сделки, у которых наступил срок автоподтверждения;
2. снимает холд по спорам, не решённым до конца срока удержания;
3. синхронизирует с провайдером холды, срок которых уже вышел;
4. закрывает неоплаченные заказы старше суток.

Без `CRON_SECRET` эндпоинт отвечает `403` и автоподтверждение не работает:
холды провисят до конца авторизации и деньги вернутся покупателям.

## Применение схемы БД

```bash
npm run db:generate
npm run db:push
```

Новые поля (`Purchase.paymentProvider`, `escrowAccumulationId`,
`splitPayoutId`, `refundTransactionIds`, `User.cloudpaymentsPayoutToken`)
добавляются как nullable либо со значением по умолчанию, поэтому
существующие покупки не ломаются: они остаются платежами ЮKassa.
Колонка идентификатора платежа сохранила прежнее имя (`yookassaPaymentId`)
и в коде называется `Purchase.providerPaymentId`.
