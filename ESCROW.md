# Безопасная сделка: холдирование + сплитование ЮKassa

Деньги покупателя не попадают продавцу сразу. Они замораживаются на карте,
товар передаётся, и только после подтверждения приёма платёж списывается и
делится: выручка — продавцу, комиссия — площадке.

Используются два механизма ЮKassa:

- **двухэтапная оплата** — `capture: false` при создании платежа и последующий
  `POST /payments/{id}/capture`;
- **ЮKassa для платформ (сплитование)** — массив `transfers` с `account_id`
  продавца и `platform_fee_amount` площадки.

## Сценарий сделки

| Шаг | Что происходит | Код |
| --- | --- | --- |
| 1 | Покупатель оформляет заказ. Создаётся платёж с `capture: false` — средства авторизуются и замораживаются на карте | [`/api/payments/create`](src/app/api/payments/create/route.ts) |
| 2 | ЮKassa присылает `payment.waiting_for_capture`. Покупка переходит в `HELD`, покупатель получает файл и лицензионный ключ | [`holdPurchase`](src/lib/purchase-fulfillment.ts) |
| 3 | Покупатель нажимает «Подтвердить получение». Выполняется `capture` с `transfers`: сумма A уходит на счёт продавца, сумма B (комиссия) остаётся площадке | [`/api/purchases/[id]/confirm`](src/app/api/purchases/[id]/confirm/route.ts) → [`settlePurchase`](src/lib/purchase-fulfillment.ts) |

Если покупатель молчит, сделку подтверждает фоновая задача — через
`ESCROW_AUTO_CONFIRM_DAYS` дней (по умолчанию 3), но всегда раньше, чем ЮKassa
снимет холд сама (обычно 7 дней с момента авторизации).

## Статусы покупки

```
PENDING ──(payment.waiting_for_capture)──► HELD ──(capture)──► COMPLETED
   │                                        │                     │
   │                                        │                     └─(refund)─► REFUNDED
   │                                        └─(cancel / истёк холд)─────────► REFUNDED
   └─(payment.canceled)──────────────────────────────────────────► FAILED
```

Товар доступен для скачивания уже в `HELD`: подтверждать покупателю нужно то,
что он реально получил.

## Куда уходят деньги

Сплитование включается, если продавец указал идентификатор своего магазина
в «ЮKassa для платформ» (`User.yookassaAccountId`, поле в разделе
«Доходы» кабинета продавца):

- **счёт указан** — при `capture` передаётся
  `transfers: [{ account_id, amount: <вся сумма>, platform_fee_amount: <комиссия> }]`.
  Продавец получает `amount − platform_fee_amount` на свой счёт в ЮKassa,
  внутренний баланс площадки не участвует;
- **счёт не указан** — платёж обычный, деньги приходят площадке, а продавцу
  начисляется внутренний баланс (`User.balance`) с выводом через заявку.

Сумма всех `transfers[].amount` должна совпадать с суммой платежа — комиссия
удерживается внутри трансфера, а не выносится отдельной строкой.

## Споры

Решение спора зависит от того, списаны деньги или ещё заморожены
([`/api/disputes/[id]/resolve`](src/app/api/disputes/[id]/resolve/route.ts)):

| Состояние | Отказ в споре | Полный возврат | Частичный возврат |
| --- | --- | --- | --- |
| `HELD` | `capture` всей суммы | `cancel` — холд снимается, деньги остаются у покупателя | `capture` части суммы, разницу ЮKassa возвращает сама |
| `COMPLETED` | ничего | `POST /refunds` с `sources` | `POST /refunds` на часть суммы |

Пока спор открыт, подтвердить сделку нельзя, а автоподтверждение её не трогает.
Если спор не решён до конца срока холда, фоновая задача снимает холд —
списать деньги после `expires_at` всё равно невозможно.

## Что настроить в ЮKassa

1. Подключить «ЮKassa для платформ» и получить `account_id` для каждого продавца.
2. Включить двухэтапную оплату в настройках магазина.
3. В разделе HTTP-уведомлений указать `https://<домен>/api/payments/webhook`
   и включить события:
   - `payment.waiting_for_capture` — деньги заморожены, выдаём товар;
   - `payment.succeeded` — списание подтверждено;
   - `payment.canceled` — платёж отменён или холд истёк;
   - `refund.succeeded` — прошёл возврат.

Уведомления принимаются только с [официальных адресов ЮKassa](https://yookassa.ru/developers/using-api/webhooks),
а их содержимое перепроверяется запросом к API — тело запроса само по себе
не является доказательством оплаты.

## Фоновая задача

```bash
curl -X POST https://<домен>/api/cron/settle-holds \
     -H "Authorization: Bearer $CRON_SECRET"
```

Запускать раз в 10–15 минут (cron, systemd timer, Kubernetes CronJob). Задача:

1. подтверждает сделки, у которых наступил срок автоподтверждения;
2. снимает холд по спорам, не решённым до конца срока удержания;
3. синхронизирует с ЮKassa холды, срок которых уже вышел;
4. закрывает неоплаченные заказы старше суток.

Без `CRON_SECRET` эндпоинт отвечает `403` и автоподтверждение не работает:
холды провисят до `expires_at` и деньги вернутся покупателям.

## Применение схемы БД

```bash
npm run db:generate
npm run db:push
```

Новые поля (`Purchase.heldAt`, `holdExpiresAt`, `autoConfirmAt`, `confirmedAt`,
`confirmedBy`, `captureStartedAt`, `capturedAmount`, `refundedAmount`,
`splitAccountId`, `User.yookassaAccountId`) добавляются как nullable, поэтому
существующие покупки не ломаются: они остаются в старой модели расчётов
по внутреннему балансу.
